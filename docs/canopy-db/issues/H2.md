# A second process cannot open an environment that another process has open

## Summary

Within one process, CanopyDB supports many concurrent readers. Across processes it does not: opening an
environment takes an exclusive lock on its folder, so a second process that opens the same environment waits
`file_lock_timeout` (5 seconds by default) and then fails with `EnvironmentLocked`, even when both processes
only want to read.

This may well be by design. If so, it would help to state it in the README, and the question is whether a
shared (read-only) opening across processes is something you would consider.

## Version

- canopydb 0.2.5
- Reproduced on Windows 11 (2026-10-21).

## Steps to reproduce

A single program that depends only on `canopydb = "=0.2.5"`. Process A creates a small environment, keeps it
open and starts itself again as process B, which tries to open the same folder:

```rust
use std::path::Path;
use std::process::{Command, ExitCode};
use std::time::Instant;

use canopydb::{DbOptions, Environment};

fn main() -> ExitCode {
    let args: Vec<String> = std::env::args().collect();
    if args.get(1).map(String::as_str) == Some("second") {
        return second_process(Path::new(&args[2]));
    }

    let path = std::env::temp_dir().join(format!("canopydb-lock-{}", std::process::id()));
    std::fs::create_dir_all(&path).unwrap();
    {
        let env = Environment::new(&path).unwrap();
        let mut options = DbOptions::default();
        options.use_wal = false;
        let db = env.get_or_create_database_with("db", options).unwrap();
        let tx = db.begin_write().unwrap();
        {
            let mut tree = tx.get_or_create_tree(b"t").unwrap();
            for i in 0u32..10 {
                tree.insert(&i.to_be_bytes(), b"value").unwrap();
            }
        }
        tx.commit().unwrap();
        db.checkpoint().unwrap();
    }

    let _held = Environment::new(&path).unwrap(); // process A keeps the environment open
    let started = Instant::now();
    let status = Command::new(std::env::current_exe().unwrap())
        .arg("second")
        .arg(&path)
        .status()
        .unwrap();
    println!(
        "process B ended with code {:?} after {:.1} s",
        status.code(),
        started.elapsed().as_secs_f64()
    );
    ExitCode::SUCCESS
}

fn second_process(path: &Path) -> ExitCode {
    let started = Instant::now();
    match Environment::new(path) {
        Ok(_) => {
            println!("process B opened the base");
            ExitCode::SUCCESS
        }
        Err(error) => {
            println!(
                "process B could not open the base after {:.1} s: {error} ({error:?})",
                started.elapsed().as_secs_f64()
            );
            ExitCode::from(3)
        }
    }
}
```

## Expected

Either process B can open the environment (at least to read it) while process A has it open, or the
documentation states that an environment can only be open in one process at a time.

## Actual

```text
process B could not open the base after 5.0 s: EnvironmentLocked (EnvironmentLocked)
process B ended with code Some(3) after 5.0 s
```

## Impact

An embedder that serves reads from several processes over the same data (for example short-lived CLI
invocations, or a reader running while a verification tool inspects the same files) has to serialize them
itself. Each extra process waits the full lock timeout before failing, and nothing in the README warns about it
up front, so the limitation tends to be discovered late, after the design assumes concurrent readers.

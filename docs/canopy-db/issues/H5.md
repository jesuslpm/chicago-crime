# Feature request: bulk load / append path for already sorted keys

## Summary

The only way to write into a tree is `Tree::insert`, one entry at a time inside a write transaction. There is
no bulk load that builds a tree bottom-up from already sorted entries (like `MDB_APPEND` in LMDB), and no
append mode. Every insert descends from the root through all the levels of the tree even when keys arrive in
increasing order.

CanopyDB already optimizes the leaf split for sequential inserts (`node_split_right` in `src/tree.rs`,
"Optimize for sequential inserts"): when the key is greater than every key of a full leaf, the leaf stays full
and the key goes to a new page. The descent is not optimized, though, and branch nodes are split in half. For
write-once workloads that produce sorted data (building an index or a snapshot from a sorted source), the
insert path dominates the cost.

## Version

- canopydb 0.2.5
- Reproduced on Windows 11 (2026-10-21), release build.

## Steps to reproduce

A program that depends only on `canopydb = "=0.2.5"`; run it with `cargo run --release`. It writes, in key
order, a primary tree of 8,656,904 entries with 138-byte values and five more trees with as many entries and
empty values, 100,000 entries per transaction, without write-ahead log and with a 64 MiB page cache, then prints
the time and the size of the files.

```rust
use std::fs;
use std::path::Path;
use std::time::Instant;

use canopydb::{DbOptions, EnvOptions, Environment};

fn size(dir: &Path) -> u64 {
    let mut total = 0;
    for entry in fs::read_dir(dir).unwrap() {
        let path = entry.unwrap().path();
        total += if path.is_dir() { size(&path) } else { fs::metadata(&path).unwrap().len() };
    }
    total
}

fn main() {
    const RECORDS: u64 = 8_656_904;
    let path = std::env::temp_dir().join(format!("canopydb-bulk-{}", std::process::id()));
    fs::create_dir_all(&path).unwrap();

    let mut options = EnvOptions::new(&path);
    options.page_cache_size = 64 << 20;
    let env = Environment::with_options(options).unwrap();
    let mut db_options = DbOptions::default();
    db_options.use_wal = false;
    let db = env.get_or_create_database_with("db", db_options).unwrap();

    let value = vec![0x42u8; 138];
    let started = Instant::now();
    for (index, name) in ["t0", "t1", "t2", "t3", "t4", "t5"].iter().enumerate() {
        let mut next = 0u64;
        while next < RECORDS {
            let tx = db.begin_write().unwrap();
            {
                let mut tree = tx.get_or_create_tree(name.as_bytes()).unwrap();
                let end = (next + 100_000).min(RECORDS);
                while next < end {
                    if index == 0 {
                        tree.insert(&next.to_be_bytes(), &value).unwrap();
                    } else {
                        // Index-like keys: a group prefix, a short tag and the record id, still increasing.
                        let mut key = (next / 1_000).to_be_bytes().to_vec();
                        key.extend_from_slice(b"value-x");
                        key.extend_from_slice(&next.to_be_bytes());
                        tree.insert(&key, &[]).unwrap();
                    }
                    next += 1;
                }
            }
            tx.commit().unwrap();
        }
    }
    db.checkpoint().unwrap();
    let elapsed = started.elapsed();
    drop(db);
    drop(env);
    println!(
        "h5) {} sorted entries in 6 trees written with Tree::insert in {:.1} s; base size {} bytes",
        RECORDS * 6,
        elapsed.as_secs_f64(),
        size(&path)
    );
    let _ = fs::remove_dir_all(&path);
}
```

## Expected

A way to load entries that are already in key order at close to sequential-write speed, with full leaf and
branch pages: either a bulk-load API for an empty tree (or for appending keys greater than the current maximum),
or an insert path that recognizes appends and skips the descent.

## Actual

```text
h5) 51941424 sorted entries in 6 trees written with Tree::insert in 31.7 s; base size 3284664620 bytes
```

The time varies between runs (the same load took 66.6 s in an earlier run on the same machine); these are not
controlled benchmark figures. A profile of the same load with cycle counters in a local copy of the crate put
99.7 % of the time inside `Tree::insert`: the commits added up to 0.1 s and the final checkpoint to less than
0.1 s, since the flush runs on another thread. The trees have four levels; per insert, the leaf takes 27–29 % of
the time and the descent through the three branch levels the rest.

## Impact

Write-once and rebuild workloads are a natural fit for an embedded B-tree store: importing a dataset, building
secondary indexes from a sorted source, or producing a read-mostly snapshot. In those workloads the data is
already sorted, and today the store cannot take advantage of it: most of the time goes into descending the
tree for every key, and the half-split branch nodes make the files larger than necessary.

## Possible fix

Two options, from smaller to larger scope:

1. **An append fast path, without new API.** The tree remembers its rightmost leaf. A key greater than the last
   key of that leaf that fits in it is inserted there directly, without descending through the branch nodes;
   otherwise the insert takes the normal path and the rightmost leaf is looked up again afterwards. Deletes,
   `delete_range`, `clear` and compaction forget the leaf, and an insert that is not an append disables the fast
   path until the end of the transaction. In a prototype on 0.2.5 (about 140 added lines in `src/tree.rs` and
   `src/lib.rs`), the crate's own tests still passed, a randomized comparison against a `BTreeMap` found no
   differences, and the load above went from 33–39 s to 13–15 s (about 2.5 times faster) with the same file
   size. I can share the prototype patch if it is useful.
2. **A bulk-load API** for an empty tree (or for appending increasing keys) that writes full leaves
   sequentially and builds the upper levels afterwards. It would gain more than the fast path, and it is the
   only one of the two that would reduce the file size, because it would also fill the branch nodes.

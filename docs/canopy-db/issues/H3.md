# No read-only opening: reading an environment requires write access and can change its files

## Summary

CanopyDB has no read-only way to open an environment. Opening it only to read opens its internal files for
writing, so:

- an environment whose files are read-only cannot be opened at all, not even to read it;
- if the environment was closed without a checkpoint, opening it only to read rewrites its write-ahead log;
- opening a database with options that differ from the stored ones rewrites its `OPTIONS` file with the
  options of the opener.

A read-only opening mode (or documentation of which of these effects are expected) would cover these cases.

## Version

- canopydb 0.2.5
- Reproduced on Windows 11 (2026-10-21).

## Steps to reproduce

A program that depends only on `canopydb = "=0.2.5"`. Part a) makes a checkpointed environment read-only and
tries to read it; part b) opens, only to read, an environment closed without a checkpoint and compares its
files before and after.

```rust
use std::collections::BTreeMap;
use std::fs;
use std::path::{Path, PathBuf};

use canopydb::{DbOptions, EnvOptions, Environment};

fn new_folder(name: &str) -> PathBuf {
    let path = std::env::temp_dir().join(format!("canopydb-ro-{name}-{}", std::process::id()));
    let _ = fs::remove_dir_all(&path);
    fs::create_dir_all(&path).unwrap();
    path
}

fn create(path: &Path, entries: u32, use_wal: bool, checkpoint: bool) {
    let env = Environment::new(path).unwrap();
    let mut options = DbOptions::default();
    options.use_wal = use_wal;
    let db = env.get_or_create_database_with("db", options).unwrap();
    let tx = db.begin_write().unwrap();
    {
        let mut tree = tx.get_or_create_tree(b"t").unwrap();
        for i in 0..entries {
            tree.insert(&i.to_be_bytes(), b"value").unwrap();
        }
    }
    tx.commit().unwrap();
    if checkpoint {
        db.checkpoint().unwrap();
    }
}

fn files(dir: &Path) -> BTreeMap<String, Vec<u8>> {
    let mut all = BTreeMap::new();
    let mut pending = vec![dir.to_path_buf()];
    while let Some(folder) = pending.pop() {
        for entry in fs::read_dir(&folder).unwrap() {
            let path = entry.unwrap().path();
            if path.is_dir() {
                pending.push(path);
            } else {
                let name = path.strip_prefix(dir).unwrap().display().to_string();
                all.insert(name, fs::read(&path).unwrap());
            }
        }
    }
    all
}

fn set_read_only(dir: &Path, read_only: bool) {
    let mut pending = vec![dir.to_path_buf()];
    while let Some(path) = pending.pop() {
        if path.is_dir() {
            for entry in fs::read_dir(&path).unwrap() {
                pending.push(entry.unwrap().path());
            }
        }
        let mut permissions = fs::metadata(&path).unwrap().permissions();
        permissions.set_readonly(read_only);
        fs::set_permissions(&path, permissions).unwrap();
    }
}

fn main() {
    // a) An environment whose files are read-only cannot be opened to read it.
    let read_only = new_folder("a");
    create(&read_only, 10, false, true);
    set_read_only(&read_only, true);
    let opened = Environment::with_options(EnvOptions::new(&read_only)).and_then(|env| {
        let entries = match env.get_database("db")? {
            Some(db) => db.begin_read()?.get_tree(b"t")?.map_or(0, |tree| tree.len()),
            None => 0,
        };
        Ok(entries)
    });
    set_read_only(&read_only, false);
    match opened {
        Ok(entries) => println!("a) the read-only base opened and holds {entries} entries"),
        Err(error) => println!("a) the read-only base cannot be opened: {error} ({error:?})"),
    }

    // b) Opening only to read an environment closed without a checkpoint changes its files.
    let unflushed = new_folder("b");
    create(&unflushed, 1_000, true, false);
    let before = files(&unflushed);
    {
        let env = Environment::new(&unflushed).unwrap();
        let db = env.get_database("db").unwrap().unwrap();
        let tx = db.begin_read().unwrap();
        let tree = tx.get_tree(b"t").unwrap().unwrap();
        println!("b) read {} entries without writing", tree.len());
    }
    let after = files(&unflushed);
    for (name, old) in &before {
        if after.get(name) != Some(old) {
            let new = after.get(name).map_or("missing".to_owned(), |b| format!("{} bytes", b.len()));
            println!("b) {name}: {} bytes -> {new}", old.len());
        }
    }
}
```

The `OPTIONS` rewrite was observed separately: a database created with `use_wal = false` and then opened
with `Environment::new` and the default options, only to read it, had its `OPTIONS` file rewritten from 300 to
299 bytes, with the stored `DbOptions` replaced by the opener's.

## Expected

- An environment can be opened to read it without write access to its folder, for example through a read-only
  opening mode.
- Opening an environment only to read it leaves its files unchanged, or the documentation says which files a
  read-only workload may still modify (write-ahead log recovery, `OPTIONS`).

## Actual

```text
a) the read-only base cannot be opened: Io(Os { code: 5, kind: PermissionDenied, message: "Access is denied." }) (...)
b) read 1000 entries without writing
b) WAL-0000000000: 1048576 bytes -> 34121 bytes
```

## Impact

Read-only consumers are common for an embedded store: data shipped on read-only media or mounts, files
published by one tool and read by another, or verification tools that must prove they changed nothing. Today
such a consumer needs write access, must make sure the writer checkpointed before closing, and must reopen with
exactly the stored options; otherwise reading alters the files it is reading, which also breaks checksums or
backups taken of them.
